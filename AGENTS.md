# glitchbox — agent notes

macOS app (Glitchbox.app) that layers glitch plugins into chains, its iPhone/iPad build (same app, every tool linked in-process), plus the seeded terminal pipelines it grew out of and `glitch-loop/`, an ffmpeg + FFglitch datamosh piece. Every tool ships inside the app bundle; there is no Nix. README.md is the product page (features, install, credits) and carries no development detail; the engineering facts live in this file, `packaging/build.sh`'s comments, and each pipeline's `--help` header.

## Layout
- `packaging/` — `build.sh [tools|app|dmg|all|verify|notarize|sources]` builds the toolchain from `sources.json` (URL + sha256 per input), stages it in `build/stage/Contents`, builds the app/CLI, assembles `build/Glitchbox.app`, signs inside-out, verifies, and makes `build/dist/Glitchbox-<VERSION>.dmg`. Stages are stamped by recipe/input hash in `build/stamps`; downloads cached in `build/downloads`. Must stay runnable by `/bin/bash` 3.2. The `licenses` stage (needs `cargo-about` 0.9.2; `about.toml`/`about.hbs`) collects every component's licence texts into `Contents/Resources/licenses/<component>/` (upstream files, GStreamer's `share/licenses` minus x264, reactive-vcr's own notices, FFglitch's QuickJS and the SDL2/zlib-ng/RtMidi/ZeroMQ it links statically, cargo-about crate lists for ntsc-rs-cli, bender, and burns, vendored `licenses/jq/COPYING`) and writes `Resources/Credits.html` (the About panel) from the `CREDITS` table, ending with the source offer (the release's link); verify fails if a credited component has no texts. Adding a bundled tool means a `CREDITS` row, a `lic_copy` line, and `"mirror": true` on its source pin. `notarize` (Developer ID identity + `GLITCHBOX_NOTARY_*` API key) notarizes and staples the app, rebuilds the DMG, and notarizes and staples that. `sources` (clean committed checkout) writes `build/dist/Glitchbox-<VERSION>-sources.tar`: `git archive HEAD`, every `mirror` input (plus `mirrorOnly` ones like GStreamer's cerbero source, fetched only here), and `cargo-home.tar.gz`, a fresh CARGO_HOME with every crate of ntsc-rs, glitchbox-fx, and glitchbox-burns (`cargo fetch --locked`; `cargo vendor` can't, since glitchbox-fx has ntsc-rs 0.1.2 from two git sources). CI runs both on release runs (`v*` tags or `release-dry-run`).
- `packaging/ios/` — the iOS toolchain, one `build.sh` stage per file (`build_ios_<name>`, keyed by `ios_<name>_srcs`/`_inputs`; `build.sh stage NAME…` runs some, `ios-tools` all). It must hold no GPL code (App Store build): `ffmpeg.sh` → `GlitchFFmpeg.xcframework` (static: FFmpeg 8.1.2 configured without `--enable-gpl`, so no x264/frei0r/GPL filters, plus fftools as `gb_ffmpeg_run`/`gb_ffprobe_run`; the stage dies unless `config.h` is the LGPL configuration), `ffglitch.sh` → `FFglitch.xcframework` (dynamic, built from the `ffglitch-src` tarball, also LGPL-checked; its FFmpeg 7.0-based libav* stay private; exports only `ffglitch_ffgac_run`/`ffglitch_ffedit_run`), `fx.sh` → `GlitchboxFX.xcframework`, `burns.sh` → `GlitchboxBurns.xcframework` + `onnxruntime.xcframework` (the official pod's static library relinked as a framework), `licenses.sh` → `build/ios/licenses` (LGPL texts, each in-process patch plus a `MODIFICATIONS.txt`; cargo-about with `packaging/ios/about.toml`, which refuses GPL crates). Every xcframework has `ios-arm64`, `ios-arm64-simulator`, and `macos-arm64` slices. `build.sh ios-app` adds `build/ios/Toolchain` (library, ffglitch-scripts, bender-presets, licenses, `Credits.html` from `CREDITS_IOS` with the kyle@klr.dev written source offer, `toolchain.json`) and a signed Release device build at `build/ios/Glitchbox.app`; `ios-install` puts it on `$GLITCHBOX_DEVICE`; `ios-archive` makes the App Store `build/ios/export/Glitchbox.ipa` (`packaging/ios/ExportOptions.plist`).
- `app/` — `project.yml` (XcodeGen, the macOS app; generated `Glitchbox.xcodeproj` is gitignored; declares the MKV UTType for export) and `ios.yml` (the `Glitchbox iOS` target and the GlitchboxInProcess package; `project.yml` includes it only when `GLITCHBOX_IOS=YES`, because SwiftPM refuses to load a package whose binary xcframework is missing, even for schemes that don't use it, and those exist only after `build.sh ios-tools`). `Glitchbox/` (SwiftUI app, `AppIcon.icon` Icon Composer icon): shared code at the top, AppKit-only files in `macOS/`, UIKit/Photos/BackgroundTasks-only files in `iOS/` (each target excludes the other's folder; `iOS/Info.plist` is generated by xcodegen and committed like `macOS/Info.plist`). `GlitchboxKit/` (macOS + iOS engine library incl. `Export/` — `ExportPlan` pure argv builder, `Exporter`, `MediaProbe` — the macOS-only `glitchbox` CLI, Swift Testing suite). `GlitchboxInProcess/` (iOS's `ToolRunner`: the tools as library calls plus native steps; macOS slices only for `swift test`; `Artifacts/` holds copies of the xcframeworks, gitignored). `rust/glitchbox-fx` (one staticlib over the media-free cores of ntsc-rs, bender, and reactive-vcr, plus the original pixel effects in `pixel.rs`) and `rust/glitchbox-burns` (cdylib over burns), each with a C header and a committed Cargo.lock.
- Library: `plugins/*.json`, `presets/` (chains, `plugins/<id>/`, `vhs.json`, `reactive-vcr.toml`), `scripts/` (ffedit scripts), `pipelines/` (+ `_lib.sh`). Copied into `Contents/Resources/library` as the built-in, read-only library.
- Simple-mode data lives in the library too: each plugin manifest's `simple` block (plain name, blurb, picker category, at most 4 controls that name real bool/enum/file/ranged params), a `category` on built-in chain presets (the Looks gallery section; user-saved chains have none and show under "My Looks"), and `presets/thumbnails/{looks,effects}/*.jpg`. `packaging/make-thumbnails.sh [TOOLCHAIN]` renders the thumbnails over ffmpeg's test card with a 120 bpm kick-and-hat track (stills get its frame at 1 s; the sound drives reactive-vcr) and rebuilds both folders; outputs are committed. block-glitch and row-shift are unseeded, so rerun once and commit all outputs together. Adding a Look or a plugin with a `simple` block means rerunning it (`BuiltinLibraryTests` fails on a missing thumbnail).
- Bundle: `Contents/Helpers/` (ffmpeg, ffprobe, ffgac, ffedit, fflive, qjs, ntsc-rs-cli, bender, burns, reactive-vcr, jq, sox, bash, glitchbox), `Frameworks/GStreamer.framework`, `Frameworks/libonnxruntime.dylib`, `PlugIns/frei0r-1/*.dylib`, `Resources/{library,ffglitch-scripts,bender-presets,toolchain.json,licenses,Credits.html}`.
- iOS bundle: `Glitchbox.app/Frameworks/{FFglitch,GlitchboxBurns,onnxruntime}.framework` (GlitchFFmpeg and GlitchboxFX link statically into the app), `Toolchain/{toolchain.json,library,ffglitch-scripts,bender-presets,licenses,Credits.html}`. User library and cache are the container's `Library/Application Support/Glitchbox` and `Library/Caches/Glitchbox`; exports go to `Documents/Exports` (visible in Files) and from there to Share, Photos, or Files.
- `glitch-loop/` — standalone datamosh loop: a still (`source=`, default `glitch-loop/source.jpg`) → judder (`filters/judder.filter`) → MPEG-2 forced-MV (`ffgac`) → `ffedit` + `scripts/mv_average_timed.js` → VHS (`filters/vhs2.filter`) → `out/loop_mosh.mp4`. `combine` layers an external video over the tail and cross-moshes (`scripts/mv_layer_mosh.js`). Its justfile puts `../build/Glitchbox.app/Contents/Helpers` first on PATH. Intermediates go to `glitch-loop/work/`, finals to `glitch-loop/out/` (both gitignored; `out/` holds the owner's finished renders — don't delete). `source.jpg` is the owner's private image: gitignored, never committed (it was removed from all history), not MIT, never used for demos or site assets.
- `site/` — static splash page (no build step; relative URLs so it works from `file://` and Pages under `/glitchbox/`). Demo clips are real renders: `site/make-demos.sh [TOOLCHAIN]` regenerates them from `site/demos/*.json` chains over synthetic lavfi sources; outputs are committed (`.gitignore` exceptions under `site/assets/`). jj won't snapshot new files over 1 MiB, so keep clips under that. The stack demo uses unseeded frei0r randomness, so rerun once and commit all outputs together.
- `.github/workflows/` — `build.yml` (xcode-27 runner, Xcode 27.0 + Rust 1.97.0 + cargo-about 0.9.2 pinned; swift test, `build.sh all`, DMG artifact; `v*` tag must equal `v$(cat packaging/VERSION)` and creates a draft release with the DMG and `Glitchbox-<VERSION>-sources.tar`). Release runs (`v*` tags, or `workflow_dispatch` with `release-dry-run`) import the Developer ID certificate into a throwaway keychain, sign with it, run `build.sh notarize` before the DMG checksum, and run `build.sh sources`; other runs stay ad-hoc. `pages.yml` deploys `site/` on release publish or manual dispatch; Pages uses Actions as source, and the `github-pages` environment allows `main` plus `v*` tags, since a release run's ref is the tag. Releasing: bump `packaging/VERSION`, push a signed `v<VERSION>` tag on green `main`, wait for the draft, check the notarized DMG and the sources tar, edit the notes, publish (that deploys the site). The repo is public, so Actions minutes are free; caches are per-branch.
- Licence: Glitchbox's own code is MIT (`LICENSE`). On macOS the bundled tools keep theirs (FFmpeg/SoX/FFglitch GPL-2.0+, frei0r GPL-2.0+ with kaleid0sc0pe and vertigo GPL-3.0+, bash GPL-3.0+, ntsc-rs-cli GPL-3.0, GStreamer LGPL); compliance mirrors ntsc-rs: licence texts in the bundle, credits with source links, and the release's source bundle. x264 is gone: H.264/HEVC encoding is VideoToolbox only. The iOS app is LGPL-2.1+ FFmpeg/FFglitch plus MIT/Apache code (its five frei0r effects are original MIT code in `glitchbox-fx`, `pixel.rs`: clean-room, never derived from frei0r source).

## Commands (verified on aarch64-darwin, macOS 27, Xcode 27)
- `just app` — `packaging/build.sh all`. Cold build compiles ffmpeg/frei0r/SoX/bash/ntsc-rs/bender/burns; ~11 min cold on the CI runner, ~2.5 min warm (app + verify + DMG). Needs Xcode, cargo/rustc ≥ 1.97 (burns-rs), cmake, curl, jq; the bundle is ~250 MB (DMG ~110 MB; ONNX Runtime is 37 MB of it), the build dir ~3.5 GB.
- `just doctor`, `just chain INPUT SEED`, `just verify-repro INPUT SEED`, `just analog|mangle|bend|reactive|sonify ...` — pipelines in the toolchain env (`eval "$(glitchbox env --root . --toolchain build/Glitchbox.app/Contents)"`). `just shell` opens a shell with the toolchain PATH first and the caller's PATH after it; `.envrc` does the same under direnv.
- `just plug validate|list|render --chain NAME|FILE INPUT|export --chain NAME|FILE --format h264|hevc|prores|ffv1|gif|png -o OUT INPUT|clean|env` — CLI built from source against this checkout's library and the `build/` toolchain. `just dev` builds/opens the Debug app (Info.plist `GBDevRoot` = the checkout).
- `cd app/GlitchboxKit && swift test` — engine tests.
- `just plug validate` (no files) checks every plugin manifest, chain preset, and plugin preset: `PresetValidator` reports undecodable files, a file name that isn't the name's slug, unknown plugins/keys, clamped or mistyped values, and a still-input layer that isn't first. `BuiltinLibraryTests` runs the same checks over the checkout in `swift test`. A preset that fails to decode is otherwise dropped from the app without a word.
- Building the app by hand: use the pinned XcodeGen (`build/work/xcodegen/xcodegen/bin/xcodegen`, unpacked by `build.sh app`). A PATH `xcodegen` without its `SettingPresets` ("No \"iOS\" settings found") generates an iOS target with no `SDKROOT`, and every simulator destination is rejected. iOS simulator: `rsync -a --delete plugins presets scripts pipelines build/ios/Toolchain/library/`, `GLITCHBOX_IOS=YES xcodegen generate`, then `xcodebuild -scheme "Glitchbox iOS" -destination 'platform=iOS Simulator,name=iPhone 17' -derivedDataPath .build/xcode-ios build` under the clean env.
- `packaging/build.sh ios-app` — the iOS toolchain stages (~20 min cold: FFmpeg and FFglitch three slices each, the Rust crates), `build/ios/Toolchain`, xcodegen with `GLITCHBOX_IOS=YES`, and a signed Release device build at `build/ios/Glitchbox.app` (~105 MB). Signing is automatic with team VR2B587B7P via the account signed into Xcode (`-allowProvisioningUpdates -allowProvisioningDeviceRegistration`). `GLITCHBOX_DEVICE=<udid> packaging/build.sh ios-install` installs it with `devicectl` (the device must be unlocked and reachable). For the simulator, generate with `GLITCHBOX_IOS=YES` and build scheme `Glitchbox iOS` for `generic/platform=iOS Simulator` (arm64 only).
- `cd app/GlitchboxInProcess && swift test` — the in-process runner and every native step on the host (needs `build.sh ios-tools`, the GlitchboxKit CLI built with `swift build` in `app/GlitchboxKit`, and this checkout's `build/Glitchbox.app` as the reference toolchain; parity tests compare against it).
- `cd glitch-loop && just base` — full 112 s render (slow). Quick smoke without touching finals: `just loop_s=1 work=/tmp/gl out=/tmp/gl base`.
- xcodebuild must run under `env -i HOME USER PATH=/usr/bin:/bin:/usr/sbin:/sbin` (it imports env vars as build settings; a stray CC/LD/SDKROOT hijacks the build).

## Invariants
- Bit-exactness: all pipeline ffmpeg calls go through `gb_ffmpeg` (bitexact flags are positional — after `-i`). ntsc-rs, bender, and reactive-vcr output (all GStreamer matroskamux, random SegmentUID) is always remuxed; SoX runs with `-D`; ffedit scripts must use seeded PRNG (QuickJS `Math.random()` is unseedable) and read params from `args.params`. `just verify-repro` must stay green. Verified: the first bundled toolchain (VideoToolbox decode) matched the old Nix toolchain — mv-mangle and chain byte-identical, analog-pass and bend frame-identical (`framemd5`). Since the GStreamer allowlist dropped `applemedia`, compressed inputs (H.264/HEVC/ProRes/MJPEG) decode via gst-libav and GStreamer-tool output differs from those renders at ~47 dB PSNR; FFV1 input (the app path) is unchanged.
- Pipeline manifests (schema 2) record `toolchain: {digest, tools}` from `$GLITCHBOX_TOOLCHAIN/Resources/toolchain.json`. The digest is sha256 over `packaging/sources.json` + `packaging/build.sh`, so editing either changes every app cache key and pipeline run ID.
- Tool environment is hermetic (GlitchboxKit `Toolchain`): PATH = `Contents/Helpers` : `<library>/pipelines` : `/usr/bin:/bin:/usr/sbin:/sbin`; only HOME USER LOGNAME TMPDIR LANG LC_* TERM pass through; plus `GLITCHBOX_ROOT`, `GLITCHBOX_TOOLCHAIN`, and toolchain.json `environment` (`FREI0R_PATH` is required — ffmpeg finds no frei0r plugins without it; `GST_PLUGIN_SYSTEM_PATH`/`GST_REGISTRY` isolate GStreamer from `~/.local/share/gstreamer-1.0` and the shared `~/.cache` registry).
- Helpers precede pipelines on PATH, so `reactive-vcr` is the binary; plugin scripts call the pipeline as `"$GB_ROOT/pipelines/reactive-vcr"`, and the pipeline itself resolves the real binary past itself (`type -ap`).
- Pipelines run on macOS userland: BSD sed/od/wc (no GNU flags like `od --endian` or `sed 's/\?//'`), `/sbin/sha256sum`, bundled bash 5 via `#!/usr/bin/env bash`.
- Library layering: user library (`~/Library/Application Support/Glitchbox`, `GLITCHBOX_DATA_DIR`) overlays the built-in one by id/name; saves go to the user library; delete removes only the user copy (reverts an override); builtin-only items can't be deleted. Cache in `~/Library/Caches/Glitchbox` (`GLITCHBOX_CACHE_DIR`).
- Simple and Advanced are two views of one session, never two states: `SessionState.studioMode` (no session file → Simple; a session without the key → Advanced; an unknown value reads as unset). Simple always auto-renders and plays the final output (`StudioModel.autoRenders`/`showsFinal`; the stored Auto-render and View Final toggles are Advanced's and untouched). Looks are chain presets, styles are plugin presets, and the effect picker and card sliders come from the manifest's `simple` block, so every Simple edit is an ordinary param edit. Plugins without a `simple` block (datascope, mv-script) stay out of Simple's picker but can sit inside Looks. `EditorDraft` carries `simple` through a plugin-editor save, pruned to controls whose param is still eligible. Loading a Look over a photo keeps the stack's still-input layer unless the Look has its own.
- reactive-vcr ("Sound Reactive" in Simple) builds its mapping from sliders (bass → tracking wobble, hits → head-switch tear, loudness → snow, highs → colour noise, settle time, hit sensitivity) unless a Map file is chosen (`map` is optional; the sliders hide behind `visibleWhen map == ""`). Two generators write the same TOML text and must stay in step: the plugin script's jq (macOS) and `ReactiveVCRStep.mapping` (iOS); `reactiveMappingIsThePluginsJq` in GlitchboxInProcess compares them and `reactiveVCRMatchesCli` renders both. reactive-vcr validates ranges against ntsc-rs bounds (`tracking_noise_wave_intensity` is ±50), so a slider's top value must stay inside them; a slider at 0 drops its `[[modulate]]` blocks. `PluginManifest.readsSourceAudio` (a step mentions `{source_audio}`/`GB_SOURCE_AUDIO`) lets the app mark such a layer "needs a sound file" on a silent source with no file param set, show that reason when its render fails, and caption its Looks "Needs sound".
- A manifest's numeric defaults are typed at decode (`ParamSpec.init(from:)`: JSON `0.0` on a float param is `.float`, not `.int`), so an untouched default equals the same value after `resolveParams` and renders as `0.0` every time. Without it a layer matching a preset exactly compared as different (`StudioModel.isActive`, the inspector's "N changed") once it had been through a session.
- App renders are best-effort reproducible (like glitch-loop), not part of `verify-repro`. Cache keys hash the parent key, plugin manifest, resolved params, file/asset digests, and the toolchain digest. File digests and ffprobe results are memoized per process by file identity (device, inode, size, mtime, ctime: any write moves ctime), so an edit doesn't re-read a multi-GB source. Argv steps get `{fps}` (and scripts `GB_FPS`): the render's exact rate (`30`, `30000/1001`), not keyed since the source layer's params fix it.
- Intermediates: source prep and every ffmpeg-written layer emit ffvhuff in MKV (lossless, deterministic, 3–4× faster than FFV1 at ~30% more disk). ntsc-rs, bender, and reactive-vcr layers stay FFV1 (remuxed; bender ≥ 0.2.1 and reactive-vcr ≥ 0.4.1 encode it threaded). Layer pix_fmts differ (yuv420p; analog-pass 4:2:0; reactive-vcr yuv444p with source SAR), so every consumer of a layer sets `-pix_fmt` and colour tags explicitly.
- Render settings are Range (whole clip / in–out) plus Resolution (short side, so portrait isn't squashed, or native) plus a rational fps from 23.976/24/25/29.97/30/50/59.94/60 or "match source" (snapped into that set, a whole multiple first so 15 → 30 repeats frames evenly, else nearest by ratio: MPEG-2 mosh rewrites other rates and desyncs). Session schema 2; schema 1 preview/full migrates on load. Source prep crops odd sizes to even (no resample), squares anamorphic pixels (a 90° autorotate inverts SAR), always writes explicit colour tags (probe, else bt709 ≥720 lines / smpte170m), relabels HDR as SDR without tone mapping (the app warns), and keeps `audio.wav` 24-bit for deeper sources. On macOS it decodes with `-hwaccel videotoolbox` only 8-bit `yuv420p` H.264/HEVC that tag their matrix and tv range (`SourcePrep.decodesInHardware`), where frames are framemd5-identical to software decoding; untagged streams (VideoToolbox guesses BT.2020 at UHD, turning the relabel into a conversion), 10-bit (`p010le` rounds differently), and ProRes differ, so they stay in software.
- Export is a separate final ffmpeg pass over the cached final layer plus the source layer's `audio.wav` (no layer processes audio), so encoder changes never re-render the chain. VideoToolbox `-q:v` is hardware-only; PCM-in-MP4 isn't offered (ffmpeg writes `ipcm`, AVFoundation won't play it). Audio length is `apad` + `-t <probed final-layer duration>`: `-shortest` cut ALAC/PCM 60–75 ms early. Output goes to a hidden partial beside the destination, then `replaceItemAt`; cancel waits for ffmpeg to exit and deletes the partial.
- Proxies (player only): `h264_videotoolbox -b:v 40M`, falling back to FFmpeg's LGPL `mpeg4 -q:v 2` (AVPlayer plays it; logged in `proxy.log`).
- The export sheet (`ExportSheet`, one for both modes) leads with three choices: Video/GIF/Frames (Video restores the last video codec), Quality (`ExportQuality` good/high/max, titled Smaller/Balanced/Best) or GIF width, and a short Size list. "More Options" unfolds the rest in place (codec, container, ProRes profile, full size menu and custom frame, range, audio, encoder; GIF frame rate/dither/palette/loop) and its state persists in `@AppStorage("exportShowsMoreOptions")`. Screenshot it expanded without touching the owner's defaults: launch with `--args -exportShowsMoreOptions YES`.
- glitch-loop is NOT bit-exact-managed (plain ffmpeg; ffvhuff intermediates, VideoToolbox H.264 finals); it's an artwork, not a pipeline.
- Packaging gotchas (verified): FFglitch, reactive-vcr, and jq prebuilts are copied byte-for-byte and keep their own linker signatures under ad-hoc signing. reactive-vcr ≥ 0.4 ships as a GStreamer .app; only `Contents/MacOS/reactive-vcr` is copied, and its `@executable_path/../Frameworks/...` rpath lands on our framework — its GStreamer version must match ours (both 1.28.8 now; bump them together). Xcode 27's `strip -S` corrupts chained-fixup Rust binaries, so ntsc-rs-cli/bender/burns ship unstripped. ffmpeg with `--disable-autodetect` needs `-liconv`. SoX 14.4.2 needs two clang fixes (see build.sh). GStreamer devel's own pkg-config is used.
- burns (Still Motion) links no GStreamer; it spawns the bundled `ffmpeg` and renders on Metal; the plugin asks it for lossless FFV1 MKV (`--codec ffv1`, burns-rs ≥ 0.2.0), which is remuxed. `--auto-depth` `dlopen`s ONNX Runtime (official Microsoft prebuilt, re-signed in `sign_app`) via toolchain.json `ORT_DYLIB_PATH` — without it burns looks only beside its own executable. The 99 MB depth model is not bundled: burns downloads it on first use into `~/Library/Caches/burns/models/<sha256>.onnx` (no flag moves it; shared with standalone burns). `sources.json` pins the model only so verify can pre-seed a private `HOME` and render a depth move offline (`smoke_burns`). burns-depth uses native-tls (Security.framework) on Apple targets, so neither app ships rustls/ring (`ITSAppUsesNonExemptEncryption` false).
- Still-input plugins (`"input": "still"`, only `still-motion`) read the original still instead of a layer: the Renderer requires a still source and that the layer be the first enabled one, runs it before source prep with a `StillTarget` (prep's rate/size for the still plus `stillDuration`/duration) exported as `GB_FPS`/`GB_DURATION`/`GB_WIDTH`/`GB_HEIGHT` and hashed into its key, then source-preps the clip at native size with the still's colour tags (export tags from the source probe). The app keeps such a layer at the top of the stack and offers it (dismissible per source) when the source is a still without one. The plugin editor preserves `input`.
- still-motion mirrors `burns schema` (v1): its params are every burns setting (per-motion ones prefixed `view_`/`start_`/`end_`/`tilt_`/`breath_`/`eight_`/`depth_`, then `shake*`, `warp*`, `seed`), and its script builds a complete project with jq and passes `--config` (strict: no missing or unknown fields, so a burns bump that changes the schema fails loudly until the plugin is updated). `presets/plugins/still-motion/` holds the 16 `burns preset` projects mapped onto those params; all 16 were verified frame-identical (`framemd5`) to `burns render --preset`. Defaults are Ken Burns. burns rejects shake whose fastest component reaches Nyquist (the vibrate presets fail at 25 fps, pass at 30). Params use `visibleWhen` (`{key: [values]}`, ANDed, transitive; validated, no cycles) so the inspector shows only the selected motion's settings; hidden params keep their values and still feed the cache key.
- GStreamer ships only the `GST_PLUGINS` allowlist in build.sh (34 plugins, from `GST_DEBUG=GST_PLUGIN_LOADING:4` traces of all three tools over MKV/MP4/MOV/AVI, FFV1/H.264/HEVC/ProRes/MPEG-4/MJPEG, PNG/JPEG stills, WAV/FLAC/AAC/MP3/Vorbis/Opus). Libraries are the @rpath closure of those plugins, the plugin scanner, and the Helpers binaries (`gst_copy_deps`); the umbrella `GStreamer` binary is an empty stub (nothing links it; the real one re-exports every library). `applemedia` stays out: its `vtdec` fails on ProRes, and software decodes are the same on every Mac. `x264` is out (GPL): the tools write FFV1/PNG only, so `ntsc-rs-cli -c h264`, `bender --codec h264`, and reactive-vcr `.mp4` output are unavailable. verify's MP4 input is VideoToolbox H.264 (MPEG-4 Part 2 where VideoToolbox is missing). Adding a plugin means adding its name to `GST_PLUGINS`; verify fails if any shipped plugin can't load or any dependency doesn't resolve.
- XcodeGen must treat `AppIcon.icon` as a file (`options.fileTypes.icon` in project.yml), or the icon's SVGs get copied into Resources instead of compiled by actool.
- macOS 27.0.1 gotchas in the app: SwiftUI `VideoPlayer` aborts in `_AVKit_SwiftUI` (use the `AVPlayerView` wrapper); `VSplitView` around the player loops AppKit constraint passes and throws; `Slider(step:)` materializes every stop (seed ranges hang the app), so `ParamControl` caps stepped sliders at 1000 stops; a grouped `Form` wrapped in a `VStack` inside `.inspector` makes the split view take its full content height and shifts every column off-screen, so the inspector's Form stays the root and its plugin header is the first section's `header:` (a `.safeAreaInset` header needs its own background, which never matches the Form's).
- App screenshots without input events: write a session.json with `"autoRender": true` into a temp `GLITCHBOX_DATA_DIR` (the app renders a restored auto-render session on launch), `open -g -n --env GLITCHBOX_DATA_DIR=… --env GLITCHBOX_CACHE_DIR=…`, then `screencapture -x -o -l <CGWindowID>`. The site's `assets/app/glitchbox-stack.png` is the `site/demos/stack.json` chain over make-demos.sh's radial `grad.mkv` at 360p, full window scaled to 1400 px.
- No Screen Recording permission (agent shells under Herdr: `CGPreflightScreenCaptureAccess()` is false and `screencapture` fails with "could not create image from window"): attach `lldb -p PID --batch` and have the app draw itself with `expr -l swift -- … v.cacheDisplay(in: v.bounds, to: rep)` on `window.contentView!.superview!`, then write the PNG. AVPlayer video and material-backed columns (sidebar, inspector) come out blank; everything else matches. Menu commands run the same way (`NSMenu.performActionForItem(at:)`); SwiftUI exposes no in-process accessibility tree to press buttons with. Simple-mode sessions render on launch without `autoRender`.
- Plugin-authoring gotchas (all verified): ntsc-rs `version: 1` presets fill missing keys from `legacy_value()`, not `Default` — `analog-pass` defaults mirror that so they reproduce `presets/vhs.json` exactly (enum values are Rust discriminants, not menu order); analog-pass renders 4:2:0 (`--chroma-subsampling`, recorded in its run ID) and, like all ntsc-rs MKV input, emits one trailing extra frame. ffedit's `-sp` JSON rejects floats, so ffedit-script params must be ints (`scripts/mosh.js` uses percents). The mosh plugins pipe `ffgac … - | ffedit -i - -o - | ffmpeg -f mpegvideo -i -`; MPEG-2 decode is nondeterministic from about frame 17, so their outputs can't be byte-checked. `pipelines/mv-mangle` pipes raw `m4v` the same way and restates the probed rate as input `-r` (`-framerate` keeps the bitstream's timestamps and drops all but 2 frames at 30000/1001); QuickJS doesn't inline, so ffedit scripts keep per-MV work inline (`mv-shuffle.js`). pixel-smear computes its brightness mask once per frame (`colorchannelmixer` → `extractplanes` → `lut`) and uses `geq` only to sample, reading `alpha()` once per plane via `st`/`ld`; a per-pixel averaging `geq` was 4.6× slower, and geq's interpreter is still ~96% of its cost (bilinear sampling at fractional coordinates, so `displace` or nearest sampling would change the look). `tblend` outputs one frame fewer. ffmpeg's frei0r filter wants bools as `y`/`n` (use enum params). frei0r `colorhalftone` renders solid black. `glitch0r`/`pixs0r` use unseeded randomness.
- FFglitch on macOS comes only from the pinned upstream macOS prebuilt in `packaging/sources.json` (never vendor binaries into the repo); iOS compiles the matching source tarball (`ffglitch-src`), and its ffgac/ffedit output is byte-identical to the prebuilt's.
- ffmpeg-filter plugin gotchas (the ten argv-only effects added with Simple mode; iOS runs them in-process, so they must stay argv steps with no bash): numbers a filter needs come straight from `{p.*}`, so anything computed must be a filter expression (enum values `"0"`/`"1"` and bools, rendered `1`/`0`, work in expressions and in `enable=`). `drawgrid` draws a vertical line at its x origin: park it off-frame (`x=iw+5:w=2*iw+20`) for scanlines only. `drawbox h=0` means full height, so gate it with `enable='gt(h\,0)'`. A chain that changes size (dither's pixel scale, old-film's weave crop) keeps a `split` of the input and ends with `[x][orig]scale=rw:rh`, the two-input scale. `palettegen` must be `stats_mode=single` with `paletteuse=new=1`: the global mode buffers the whole clip in memory. `overlay` defaults to yuv420 output (`format=gbrp` keeps RGB). `tpad=start=N` only takes a literal. interlace's field delay drops one field, so its output is a frame shorter (like `tblend`). Expression `random()` is deterministic across runs (old-film, verified by framemd5).
- ffmpeg threads and memory (every ffmpeg step; iOS pays all of it in one process): auto threads give the ffvhuff decoder and encoder one frame thread per core, each holding frames (~500 MB at 1080p, ~2 GB at 4K). Plugins decode with `-threads 6` before `-i {in}` and encode with `-threads:v 3` (source prep `-threads:v 2`, mosh chains 2; proxies and exports decode with 4): same bytes, wall within noise, peak 140–290 MB at 1080p. An output `-threads` also sets the `-vf` graph's slice threads unless `-filter_threads 0` is given (glow 2× slower, false-colour's frames change), so pair them. `pseudocolor` (false-colour) output depends on the slice count, so it already differs between Macs and iPhones.
- Staged filtergraphs (crt, vhs-filter): one ffmpeg run can split a chain whose slow filters don't slice-thread (drawgrid, vignette) into 2–3 graphs joined by loopback decoders (`-map … -c:v rawvideo -f null -` then `-dec N:0` and `[dec:N]` in `-filter_complex`), so they work on different frames at once. Identity rules: cut only where the link is already the format the next filter negotiated (`-print_graphs`) and end each stage with that `format=`; a cut in RGB is not identical (the RGB→YUV matrix changes across a loopback). Label and `-map` every intermediate output. The final output must restate `-r {fps}` (exact rational; `29.97` breaks identity) and `-disposition:v:0 default`, which a loopback-fed stream loses; after a non-default input (mosh, still-motion) FlagDefault therefore goes 0 → 1, same frames.
- iOS cannot spawn processes, so GlitchboxKit runs every tool through a `ToolRunner` (`ToolEnvironment.runner`): macOS's `SpawnRunner` is the old `Spawner` + PATH lookup and has no native steps; iOS's `InProcessRunner` (app/GlitchboxInProcess) has only ffmpeg, ffprobe, ffgac, and ffedit, run as library calls on 16 MB-stack threads. A plugin step runs as its `native` implementation whenever the runner has one (`PluginStep.native`, an engine id; the seven script/pipeline plugins and the five pixel effects carry one named after the plugin), else as argv if the runner has `argv[0]`, else as its bash script if the runner has `bash`; `requires` is checked only when some step spawns. Availability in the UI and CLI uses the same rule (`ToolEnvironment.missing(for:)`). Source prep's audio step is an ffmpeg argv writing `{layer}/audio.wav` (`{layer}` = the layer's partial directory). User-written script plugins don't run on iOS.
- In-process tools: fftools globals (ffmpeg/ffprobe, and ffgac/ffedit separately) live in renamed data sections that are restored from a load-time snapshot before every run, so each run behaves like a fresh process; `exit()` is hooked (FFglitch) and ffprobe's exits return errors; cancel is a per-run flag polled where SIGTERM would act, and also while a run waits for its tool's lock. Each tool is serialized against itself (ffmpeg and ffprobe share one lock), so an export waits behind a render's ffmpeg step; ffgac, ffedit, and ffmpeg run concurrently in the mosh plugins, joined by `pipe:N` fds the host closes as each stage returns, and whole multi-tool chains pass one at a time through `ChainGate` (two chains taking the per-tool locks in different orders deadlocked). Log lines go to a run's log only from threads tagged with its run (the run thread and every thread fftools or libav* create during it; `gb_thread_tag`); other threads keep the default logger. There is no SIGKILL in-process: a filter that never returns hangs its tool for the session.
- iOS native steps reproduce the macOS scripts: the FFglitch plugins with the same argv; analog-pass, bender, and reactive-vcr decode with GBMedia, convert to RGB exactly as GStreamer's videoconvert/videoscale would (checked byte-for-byte against gst-launch), run the Rust core, and encode FFV1 with the CLIs' tags (≥ 51 dB vs macOS, same frame counts incl. ntsc-rs's N+1 frame on millisecond-timestamped MKV); still-motion renders frames with GlitchboxBurns (byte-identical to `burns frame`) and encodes FFV1 as `burns --codec ffv1` does. Its depth model downloads on first use into `$BURNS_CACHE` (`@cache/burns`). wgpu's default limits exceed the iOS simulator's GPU, so glitchbox-burns caps each at what the adapter supports. block-glitch, row-shift, plasma-distort, kaleidoscope, and vertigo run `PixelEffectStep` (glitchbox-fx `gbfx_pixel_*`, original effects that look different from frei0r's; the random ones are seeded per frame index) and write ffvhuff with the input's colour tags. Every native step runs through `FramePipeline`: decode, effect, and convert+encode on three threads over a fixed pool of reused frame buffers, each stage in frame order, so outputs match the single-threaded loop byte for byte (20–45% less wall); native decoders use 2 threads and pixel effects encode on 1 (frame threads cost ~290 MB for nothing). `InProcessBench` (opt-in, `GB_BENCH=<plugin>`) prints a layer's wall, CPU, and peak phys_footprint.
- iOS exports: ffmpeg allows VideoToolbox `-q:v` only on Apple silicon Macs and `prores_videotoolbox` only on macOS (`ExportPlan.EncoderSupport`), so iOS H.264/HEVC use a bitrate from the same quality scale (0.2 bits/pixel/frame for H.264 at High, ×2 per +10, HEVC ×0.6) and ProRes uses `prores_ks`.
- iOS layout: `StudioRootView` shows the three-column `MainView` only when the window is ≥ 1000 pt wide (iPad landscape, 13-inch portrait); otherwise `CompactStudioView` (viewer over the stack, library and inspector as sheets). Portrait iPads with three columns overlay the viewer. On iOS the inspector is attached to the detail column (attached to the split view it floats over the detail and hides its toolbar), shared sheets are applied once on `StudioRootView` so a layout switch keeps them, and multiple scenes are off (one `StudioModel` drives every sheet and the single `BGContinuedProcessingTask`, which reports success only for a finished export or a completed render).
- Layout by mode: Simple uses `SimpleWideView` (looks, effect cards, viewer in a plain HStack) on the Mac and in iOS windows ≥ 1000 pt, and `iOS/SimpleCompactView` (viewer over a Looks/Adjust switch) otherwise; Advanced keeps `MainView`/`CompactStudioView`. `StudioRootView` (one per platform) switches on the mode and carries `StudioPresentations`, so changing mode keeps sheets open. There is no mode control: Simple has doorways (`StudioModel.openAdvanced(layer:)` from a card's "All Controls…", which selects that layer and raises `layerToInspect` for the Advanced layout to open its inspector, and from the effect list's footer), Advanced has `SimpleModeButton` at the leading edge of its toolbar, and ⌘1/⌘2 plus `StudioMoreMenu` cover both. Simple's viewer placeholder distinguishes waiting/rendering/making the proxy (`isRenderPending`, `isRendering`, `isMakingProxy`) from a stopped or failed render, which gets the toolbar's Render button back.
- iOS imports: picked or dropped files are copied into `<user library>/imports/<uuid>/` (excluded from backup); a non-allowlisted still (HEIC from Photos) becomes a PNG, upright, at full size, so `SourcePrep.isStill` sees it. Import folders that no session, export setting, layer, or user-library JSON mentions are deleted on launch and after each session or export-settings save.
- iOS full screen (Simple only): `LookSwipeViewer` wraps `ViewerView` in both Simple layouts. A downward drag (or the toolbar's Full Screen button) sets the layout's `isFullScreen`, which hides everything else and the bars (`FullScreenChrome`) and resizes the one viewer rather than swapping it; there, a sideways drag (or the bar's chevrons) loads the next or previous look in gallery order, skipping looks the source can't run, and a second downward drag or the close button leaves. AVKit's transport controls are off in full screen (`\.playerShowsControls`), so nothing competes for the swipes; inline they stay, and the downward swipe is a `simultaneousGesture` beside them. `StudioModel.recognizeAppliedLook` matches a restored session's layers to a library look, so the first swipe after a relaunch doesn't ask about changes nobody made.
- Driving taps and swipes on the simulator (`simctl` can't): generate a scratch project from a throwaway xcodegen spec that includes `project.yml` and adds a `bundle.ui-testing` target depending on `Glitchbox iOS` plus a scheme with a test action, then `xcodebuild … -scheme <scheme> -destination 'platform=iOS Simulator,id=…' test`. The XCUITest sets `launchEnvironment["GLITCHBOX_DATA_DIR"/"GLITCHBOX_CACHE_DIR"]` to host paths holding a seeded `session.json` (the simulator shares the Mac's filesystem, and the test can write screenshots to `/tmp` the same way). Delete the spec, sources, and project afterwards.

## Platform gaps
Apple silicon only: macOS 26+ and iOS/iPadOS 26+ (iOS simulator arm64 only). No Linux, no Intel. macOS release builds are Developer ID signed and notarized in CI (local builds stay ad-hoc unless `GLITCHBOX_SIGN_IDENTITY` and the notary key are set). The iOS build is LGPL-only for App Store distribution (team VR2B587B7P, with the increased-memory-limit and extended-virtual-addressing entitlements; `ITSAppUsesNonExemptEncryption` false; `Glitchbox/iOS/PrivacyInfo.xcprivacy`); FFmpeg/FFglitch are linked statically under LGPL-2.1 §6(a) (the whole app's source and build scripts are public, so users can relink). FFmpeg's software H.264/HEVC/AAC decoders remain on both platforms (patent licensing is the owner's call).
